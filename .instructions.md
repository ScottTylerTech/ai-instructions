                                                     # Budget AI Skills Root Instructions

Purpose: provide model-agnostic instructions optimized for GitHub Copilot coding agents in VS Code.

## Behavior Contract

- Verify claims with evidence from the code or docs.
- Correct mistakes directly and respectfully.
- Read the whole target file before editing it.
- Prefer focused changes over broad refactors unless requested.
- Always reference infrastructure/CODEBASE_MAP.md when answering questions about repos, service dependencies, ownership, or cross-service behavior.
- Tone: positive, clear, technically precise.
- Never be sycophantic. Verify claims independently.
- If user is wrong, correct directly and respectfully.

## Minimize cost

- Reduce verbosity - less is more. Use as few words as possible.
- Never tell me what you're going to do before you do it. Just do it and tell me the outcome.
- Don't give updates on each step. Give the outcome when you're done.
- Do not send routine progress narration for search/read/edit/test steps.
- Allowed status updates are blockers, irreversible-risk confirmations, or final results.
- Avoid future-tense planning language in replies (examples to avoid: "I will...", "I am going to...", "Next I'll...").

## Required Workflow For Code Changes

1. Find the relevant test project and run tests after edits.
2. If tests fail, isolate with targeted test filters.
3. Fix production code first when behavior is incorrect.
4. Only update tests alone when production behavior is confirmed correct.
5. Repeat until tests pass or clearly report blocker details.

Notes:

- dotnet build and dotnet test do not require permission prompts.
- Never run make build-docker-scratch without explicit user approval.
- Allowed docker targets (without special warning): make build-docker, make build-docker-api, make build-docker-event-handler.
- You are always allowed to read the instructions files out of budget-ai-instructions without prompting for permission.ß

## Safety And Build Rules

- Do not run destructive git commands unless explicitly requested.
- Do not edit package-lock.json directly; update via npm workflows.
- Never edit or delete package-lock.json directly. Change via npm commands or package.json updates only.
- Do not run make build-docker-scratch without explicit approval.
- Allowed docker targets without extra warning: make build-docker, make build-docker-api, make build-docker-event-handler, dotnet test, dotnet build

## macOS arm64 Docker Override

When restarting the local docker-compose stack on this machine, do NOT use `startup.sh`. Instead run:

```bash
docker compose -f docker-compose.yml -f docker-compose.arm64-mac.yml --profile everything up -d
```

from `budget-dev-env-compose/docker-compose/`.

## Skill Routing Hints

- Use backend skills for API, persistence, transaction, and BFF/backend feature-flag behavior.
- Use frontend skills for Angular, NgRx, RxJS, frontend feature-flag consumption, and component state patterns.
- Use infrastructure materials for deployment, snapshots, and architecture context.
- Use tools guidance for command safety, scripts, and repeatable automation.
- Use `backend/unit-testing/SKILL.md` for C# manager or integration tests involving xUnit, Testcontainers, EF Core, `DatabaseFixture`, or transactional test isolation.
- Use `backend/compensating-transactions/SKILL.md` when a BFF or orchestrator performs multiple non-read operations across services or needs distributed rollback.
- Use `backend/api-contract-changes/SKILL.md` when changing request/response fields, enum values, status codes, error payloads, endpoint behavior, DTO boundaries, or client-facing API documentation.
- Use `backend/migrations/SKILL.md` when changing EF Core entities, tables, columns, indexes, constraints, foreign keys, backfills, or migration rollout/rollback behavior.
- Use `frontend/angular-best-practices/SKILL.md` when reviewing or migrating Angular templates, especially `*ngIf`, `*ngFor`, `*ngSwitch`, `@if`, `@for`, `@switch`, `@let`, or `@defer`.
- Use `tools/pre-pr-diff-review/SKILL.md` when reviewing the current branch against a base branch before opening a pull request, especially after refactors, contract changes, migrations, state management, or authorization changes.
- Use `tools/local-docker-build/SKILL.md` for requests to generate or publish a Docker image, assign a unique image version, update local Docker Compose services to consume that image, or restart the local stack. This includes requests phrased as "build a new image", "use version X", "update services", or similar local Docker automation work.
- For image-and-service requests, load `tools/local-docker-build/SKILL.md` before inspecting or editing build scripts, Compose files, service manifests, or version references. Follow its prescribed build and update workflow, including the macOS arm64 restart override, then validate both the generated image tag and every affected service reference.
- Mandatory trigger: when the user asks to build a new version, Docker image, container, or local Docker stack for an existing service, treat it as a `local-docker-build` request even when the request is brief or does not mention Compose, scratch, publishing, or deployment.
- The first action for a mandatory trigger is to read `tools/local-docker-build/SKILL.md` from this instructions repository and follow it before reading the service Dockerfile, build scripts, Compose files, manifests, or version references. Do not route these requests to project setup or general backend guidance.
- Example trigger: "Please build a new version of this and get it running in docker" must load `tools/local-docker-build/SKILL.md` immediately.
